# 实验室笔记：优化差在哪（对内）

> **对外社区博客请读：[blog-arma-optimization.md](blog-arma-optimization.md)**  
> 下文保留门禁式写法，供对照 `docs/11`–`18` 与 `extract/cpu_samples/`。

---

## 1. 先澄清：玩家骂的「优化」，往往不是同一件事

| 玩家说法 | 常被当成的原因 | 本仓库测到的主因 |
|---|---|---|
| 「降分辨率也不涨帧」 | GPU 驱动差 / DX11 老 | **CPU 模拟瓶颈**（半采样率 FPS +6%） |
| 「开了多核还是卡」 | 没开多线程 | 主线程在**编排**，AI/寻路已在作业线程，但**工作量本身**太大 |
| 「画质拉满才卡」 | 渲染太重 | 核显上驱动占比可不低，但 YAAB 上仍是 **引擎算力 + 场景复杂度** 主导 |
| 「改几个脚本就能救」 | SQF 慢 | 脚本可以雪上加霜；**步兵 AI 移动**才是可量化的大头 |
| 「换引擎 / 换语言加速」 | C++ 不够快 | Profile **极平坦**，没有占支配地位的热叶子可替换 |

一句话：**不是「某一行代码写砸了」，而是「沙盒模拟的目标函数」和「玩家对 60FPS 的预期」不对齐。**

---

## 2. 为什么体感特别差：设计目标决定了成本曲线

Arma 这类军事沙盒要同时做四件事：

1. **大规模 AI**（感知、路径、战斗状态）  
2. **大地图流式加载**（地形、杂物、物体）  
3. **物理与载具**  
4. **可编辑任务 / 脚本扩展**

这四件事都随「场景里活着的实体数」近似线性（或更差）增长。现代主机 3A 往往用：

- 严格的流送预算与实例上限  
- 烘培导航、简化 AI  
- 电影镜头外卸载  

来**砍工作量**。沙盒若砍同样狠，玩法就空了——于是成本被留给 CPU。

本机 YAAB（固定视距）对照：

| | 全采样 | 半采样率 |
|---|---|---|
| Avg FPS | 64.8 | 68.6（+6%） |
| 结论 | — | **CPU-bound** |

降分辨率几乎救不了帧率时，再骂「显卡优化差」会找错科室。

---

## 3. 具体差在哪：三条证据链

### 3.1 主线程不是「算疯了」，是「排到爆」

静态上，`World::Simulate` 约 11KB、232 次直接调用、129 个目标；AI / 寻路 / clutter 以 `InvokerLambda` 形式进作业线程。  
动态上，YAAB 的 RIP 采样里：

- 原始命中大量落在 `ntdll`（等待偏差，**不是** ntdll 在算）  
- 去掉等待后：引擎约 2/3，核显 UMD 约 1/4，PhysX ~8%  
- **exe 内部 Top1 只约占 exe 命中的 1–2%，分布极平坦**

含义：

- 没有「优化这一个函数就涨 20% FPS」的开关；  
- 把 `World::Simulate` 改成 Rust **不可行**（状态与编排中枢）；  
- 「已经多线程了为什么还卡」——因为并行的是**作业**，主线程仍要每帧把世界推进一步，且作业队列可以很长。

### 3.2 差在「活物在动」，不在「路点写多了」

无头 DS 上用同一套 `gpsample` 做 AI × 路点网格（指标用 **exe_fn**，不用被封顶的 `diag_fps`）：

| 发现 | 数据直觉 |
|---|---|
| 开销 ≈ **线性于 AI 人数** | 巡逻 `exe_fn ≈ 2.69·U`，站岗 `≈ 1.02·U`（R²≈0.98） |
| 移动约 **2.6×** 站岗 | 同人数，禁 PATH 比 CYCLE 巡逻便宜一个数量级档 |
| 路点条数 1 / 2 / 5 | 已在移动时 exe 几乎不变；**是否移动**才是阶跃 |

所以任务作者常踩的坑是：

- 地图上铺满「看起来很忙」的巡逻组；  
- 以为「少写两个 waypoint」能优化——**测下来几乎白做**；  
- 调 `setSkill` 当性能旋钮——**本负载下与 0.1/1.0 无差**。

### 3.3 画面线：能改「观感」，难改「帧时」

同仓库画面旁路结论（简述）：

- tonemap / 环境光 / 曝光钳制：能改成像，**不是**帧率银弹；  
- 接触阴影 / 干净深度 / G-buffer 法线：多条 **NO-GO 或搁置**；  
- 在 CPU-bound 场景加全屏效果，更容易变成「更卡的好看」。

玩家把「画面糊 + 帧数低」捆成「优化差」；工程上应拆开：**模拟预算** 与 **后处理预算**。

## 4. 如何优化：按角色分层（只写测得动的）

### 4.1 任务 / 模组作者（收益最大、可复现）

**优先做**

1. **减活物**：少组、少人数；预算用站岗当量  
   `SEU = U_stand + 2.63 × U_move`（见 docs/17、18）  
2. **能站岗就禁移动**：`disableAI "PATH"` / `"MOVE"`，别给装饰性单位 CYCLE  
3. **脚本节流**：少按帧 `nearEntities` / 全图扫描；事件驱动  
4. **载具与 PhysX**：轻量载具增量有限，但仍占 active 样本一小块——能少则少  

**别指望**

- 微调 skill、少写几个 waypoint、换 SQF 方言「魔法加速」  
- 单叶子二进制补丁救帧（profile 太平）

**验收**

- 客户端：同画质 YAAB 或 PresentMon，固定视距  
- 服务端：`gpsample` 的 exe_fn / exe%，**不要**信本机 DS 的 `diag_fps≈28`  
- 跨 CPU：先本机标定 SEU 预算，再按单线程分缩放（docs/18）

### 4.2 玩家（画质菜单里真正有用的旋钮）

在 **已确认 CPU-bound** 的前提下：

| 更有效 | 更无效 / 次要 |
|---|---|
| 视距 / 物体视距 / 场景复杂度 | 单纯降分辨率 |
| 阴影距离、MSAA、部分后处理（减 draw → 减驱动） | 「再买一张更贵的卡」却不减 AI 负载 |
| 关不必要模组（脚本与物体） | 只改各向异性过滤指望翻倍帧率 |

核显机器上，驱动占比可观（本机 C1b 去等待后 UMD ~23%）：减 MSAA/重 PP 有意义；但 YAAB 仍显示 **砍场景复杂度** 才是主杠杆。

### 4.3 引擎 / 注入向（高成本、低确定性）

适合研究，不适合当「优化补丁」承诺：

| 方向 | 裁决 |
|---|---|
| 替换 `World::Simulate` | NO-GO |
| 热叶子 SIMD/Rust | 平坦 profile → 预期 &lt;1% 量级 |
| 后处理换算法（ACES 等） | 画质向 GO；帧率非目标 |
| Present 接触阴影 | 搁置（黑天等问题） |

## 5. 「优化差」的更准确表述

更公平的说法不是「程序员工资没交够」，而是：

1. **产品选择了高保真沙盒**，成本曲线故意陡；  
2. **主线程编排 + 海量作业** 的结构，导致「有多核却像单核」的体感；  
3. **内容侧（任务 AI）** 比渲染参数更容易把机器打满，且缺乏对作者可见的成本表——直到用采样量出来；  
4. 社区习惯用「降画质」调试，而真瓶颈在 **CPU 工作量**，于是长期觉得「怎么调都没用」→ 「优化差」。

优化的正确姿势是：**先定瓶颈（C0），再定对象（内容 vs 驱动 vs 叶子），再向量化验收**——而不是先上补丁再祈祷 FPS。

## 6. 实操清单（可今天就做）

```text
□ 半分辨率 / 半采样：FPS 涨幅 <15%？→ 按 CPU 方案做，别只砸 GPU
□ 任务：统计移动 AI 与站岗 AI → 算 SEU → 对照 docs/17 斜率
□ 装饰单位：禁 PATH；巡逻组合并、减人数
□ 脚本：去掉按帧全图查询
□ 客户端：固定视距跑 YAAB 记 Average FPS 作机型锚点
□ 跨机器：填 config/cpu_catalog.json 后用 tools/estimate_mission_cpu.py
```

## 7. 结语

游戏「优化差」的体感，往往来自：**在错误的旋钮上用力**，以及 **引擎诚实地把沙盒成本开给了你**。  

差在具体处，是 **CPU 侧世界步进与 AI 移动工作量**，外加核显路径上的驱动开销；不是「少写两个路点」或「换一门更快的语言重写主循环」能一次性赎买的。  

能落地的优化，是 **内容预算（SEU）+ 测量门禁 + 有节制的画质**；把期待从「黑科技补丁」转到「可计算的场景设计」，帧率讨论才会从玄学变成工程。
